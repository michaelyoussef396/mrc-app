## C. BUG-17 IN FULL — an operation gated on a check ran anyway

- Class: **Operation gated on a check that runs unconditionally.** The check ran, the check failed, the action happened anyway, because the action was chained after the check with `&&`, `;` or a newline instead of being gated on the check's exit status.
- Instance 1 (Session E, 2026-09-05): a Python script wrote the redacted `docs/MRC_MASTER_BACKLOG.md`, then an assertion in the same script failed. The `rm docs/_INBOX_MASTER_BACKLOG.md` that followed in the same shell command ran regardless. The inbox was deleted before its verification completed. Michael still had the original, so nothing was lost.
- Instance 2 (Codex plugin issue #653): a bad `--base` argument exits 0, so the review proceeds against the wrong target and widens scope silently. Same shape: the guard is present, the guard does not hold, the action proceeds.
- Root cause of the failed check itself: a line-count assertion compared Python `splitlines()` (2,568) against `wc -l` (2,567). They differ by one when the file has no trailing newline. This trap is independent of the class above and will recur wherever two counting methods are mixed.
- Why it was hard to find: the destructive step succeeded and printed nothing. The only sign was a traceback above it, from a check that looked unrelated to the deletion.
- Fix pattern: put the guarded action inside the same process as the check, after the assertion, so a failed check cannot reach it; or chain it with `&&` on the check's exit status and nothing else. Never place a destructive step after a script whose failure does not stop the shell. For counts, compare like with like: count newline characters, or use one tool for both sides.
- Status: logged tonight, not in the backlog, ledger entry to be written in the ledger session.

### ii. What BUG-17 actually is

The class is an operation gated on a check that runs unconditionally. Instance two: Codex plugin #653, where a bad `--base` exits 0 and the review runs against the wrong target. The fix pattern: a destructive step lives inside the same process as its check, after the assertion, or is chained with `&&` on the check's exit status and nothing else; never after a script whose failure does not stop the shell. For counts, compare like with like.
